# Go 固有のレビューチェック項目

SKILL.md の汎用チェックリストに加え、Go コードでは以下を確認する。

## エラーハンドリング
- `error` 戻り値を `_` で無視していないか（意図的なら `//nolint` コメント必須）
- `fmt.Errorf("...: %w", err)` (もしくはxerrors.Errorf)でラップしているか（スタックトレース代わり）
- `errors.Is` / `errors.As` を使って判定しているか（文字列比較していないか）

## 並行性
- `go func()` 内で外側ループ変数をキャプチャしていないか（Go 1.22 未満で問題）
- `sync.WaitGroup` の `Add` がゴルーチン起動 *前* に呼ばれているか
- `context.Context` が関数の第一引数で伝播されているか
- `select` に `case <-ctx.Done()` が含まれているか（長時間処理）
- channel のクローズ責務が明確か（送信側のみがクローズする原則）

## defer の落とし穴
- `defer` の引数は宣言時に評価される — 遅延評価が必要ならクロージャを使う
- ループ内の `defer` はループ終了まで解放されない — 関数に切り出す
- `defer rows.Close()` は `err != nil` チェックの後に書く

## スライスとマップ
- `append` の結果を元の変数に再代入しているか
- `make([]T, 0, hint)` でキャパシティヒントを与えているか（サイズ既知の場合）
- マップの nil チェック — 未初期化マップへの書き込みは panic

## インターフェース
- インターフェースは利用側（consumer）で定義しているか（Go の慣習）
- 不要に大きなインターフェースを要求していないか（ISP）

## テスト
- `t.Parallel()` を使う場合、テストケース変数のキャプチャに注意（Go 1.22 未満）
- `t.Cleanup` でリソース解放しているか
- テーブル駆動テストで `tt := tt` しているか（Go 1.22 未満）

## パフォーマンス
- `string([]byte)` / `[]byte(string)` の不要な変換が繰り返されていないか
- `sync.Pool` が適切な場面で使われているか（高頻度アロケーション）
- `strings.Builder` を使うべき場面で `+` 連結していないか
