# バックエンド機能開発

バックエンド寄りの機能追加・改修を、**要件 → 調査 → 計画 → 実装 → テスト → 自己レビュー（レビュー用SKILL必須）→ 報告** の順で進める。小さな変更でも影響調査を省略しない。

## 基本原則

- 実装に入る前に、要件・制約・成功条件を短く言語化する。
- 既存のパターン（ルーティング、永続化、トランザクション、エラー、ログ、認可）を先に把握する。
- 実装後は必ずテストと自己レビューまで行う。自己レビューは**レビュー用SKILLを読んだうえで**その手順・観点・出力形式に従う。
- レビュー用SKILLが利用できない場合は、**独自の簡易レビューに進む前にユーザーに確認**する。

## レビュー用SKILLの参照（自己レビュー工程・必須）

自己レビューを開始する前に、次の順で **`code-review`（コードレビュー）SKILL の `SKILL.md` を読み取る**（先に見つかったパスで十分）。

1. 利用可能な Agent Skills の一覧に `code-review` がある場合、その `SKILL.md` の絶対パスを開く。
2. **ワークスペース内の `.claude/skills/code-review/SKILL.md`**（本リポジトリではここに同梱されている想定）
3. `~/.cursor/skills/code-review/SKILL.md`
4. 上記が無い場合は、ワークスペースを `code-review` と `SKILL.md` で検索する。

**必須**: 読み取れた場合、そのSKILLに書かれたチェックリスト・深刻度ラベル・**出力フォーマット**に従い、変更差分（または関連ファイル）に対する自己レビュー結果を出す。独自のレビュー見出しやラベル体系で代替しない。

**見つからない場合**: 「レビュー用SKILLが見つからない」と述べ、ユーザーに (a) `code-review` SKILL のパスを教えてもらうか、(b) このタスクだけレビューSKILLなしの簡易自己チェックを許可するか、を問う。**(b) の明示承認がない限り、タスク完了扱いにしない。**

## 厳密ワークフロー

作業ごとに進捗を追えるよう、チェックリストをコピーして更新する。

```
Task Progress:
- [ ] 1. 要件・制約・非目標の整理
- [ ] 2. 既存コード・契約（API/DB/ジョブ）の調査
- [ ] 3. 実装計画（タスク分割・リスク・ロールバック）
- [ ] 4. 実装
- [ ] 5. テスト（単体/結合の適切な方）
- [ ] 6. 自己レビュー（code-review SKILL 適用済み）
- [ ] 7. 最終報告
```

### 1. 要件・制約

- ユーザーが求める振る舞い、入力/出力、エラー時の期待、互換性（後方互換・フラグ）、セキュリティ（認可・秘密情報）を整理する。
- 不明点は推測で埋めず、質問するか「仮定」として明示する。

### 2. 調査

- 変更点に関係するモジュール、既存の類似実装、設定、マイグレーション方針を特定する。
- DB変更がある場合: スキーマ、インデックス、マイグレーション手順、データ移行の有無を確認する。

### 3. 実装計画

- タスクを小さく分割し、順序と依存を書く。
- リスク（デッドロック、N+1、レース、権限漏れ、デプロイ順）を列挙する。

### 4. 実装

- 既存のスタイルとエラーハンドリングに合わせる。
- 公開API・永続化フォーマットの破壊的変更は明示し、必要なら移行策を添える。

### 5. テスト

- 重要な分岐・エラーパスをカバーする。
- 外部依存はモックまたはテスト用DB/コンテナ等、プロジェクトの慣習に従う。

### 6. 自己レビュー（code-review SKILL 必須）

- 上記「レビュー用SKILLの参照」を実行したうえで、**そのSKILLの出力フォーマットで**レビューする。
- CRITICAL/MAJOR が残る場合は、修正するか、残す理由とリスクをユーザーに明示する。

### 7. 最終報告

- 変更概要、影響範囲、実行したテスト、レビュー結果の要約（マージ可否の判断材料）を述べる。

## 判断ルール（バックエンド重点）

- マイグレーション: 本番適用順、ロールバック、ロック時間、バックフィルの有無を考慮する。
- 認証・認可: デフォルト拒否、スコープ漏れ、IDOR になりうるパスを疑う。
- エラー: 呼び出し元に返す情報とログに残す情報を分ける。秘密を返さない。
- 並行性: 共有状態、トランザクション分離、リトライの冪等性を確認する。
- パフォーマンス: N+1、不要なフルスキャン、ホットパスでの過剰アロケーションを疑う。

## 出力テンプレート

実装タスクでは、次の順で出力する（不要なセクションは「該当なし」と明記）。

### A. 調査メモ

```markdown
## 調査メモ

### 現状
- ...

### 関連ファイル・モジュール
- ...

### 制約・懸念
- ...
```

### B. 実装計画

```markdown
## 実装計画

### タスク
1. ...
2. ...

### リスクと対策
- ...

### ロールバック / フラグ
- ...
```

### C. テスト結果

```markdown
## テスト

### 実行したこと
- ...

### 結果
- ...
```

### D. 自己レビュー（code-review SKILL に従う）

- **code-review の `SKILL.md` を読んだ後**、その文書の「出力フォーマット」セクションどおりに出力する。
- セクション見出しは code-review 側の定義に合わせる（独自フォーマットにしない）。

### E. 最終報告

```markdown
## 最終報告

### 概要
- ...

### 変更点
- ...

### テスト
- ...

### 自己レビュー要約
- ...

### 次のアクション（あれば）
- ...
```

## 追加リソース

- 言語やフレームワーク固有の深いルールが必要になったら、`references/` に分割した別ファイルを同ディレクトリに置き、本SKILLから1階層だけリンクする（任意）。
