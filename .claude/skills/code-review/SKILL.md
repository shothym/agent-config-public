# コードレビュースキル

シニアエンジニア水準の構造化されたコードレビューを実施する。目標は**実行可能な批評**であり褒め言葉でも粗探しでもない。すべての指摘は*なぜ問題か* と *何をすべきか* を必ずセットで伝える。

---

## レビューの哲学

- **深刻度を最優先。** すべての問題は等価ではない。必ず重要度をランク付けする。
- **リスクを説明する。** 「これは間違い」は無意味。「並行アクセス時にデータレースが
  発生する。なぜなら〜」が有用。
- **批判だけしない。修正案を示す。** 修正後のコードか、具体的な方向性を提示する。
- **意見と事実を区別する。** スタイルの好みは述べてよいが、明確にラベルを付ける。
- **過大評価しない。** 深刻な問題があれば、はっきりそう言う。
- **量より質。** CRITICAL / MAJOR を最優先で伝える。NIT は最大 5 件に絞り、
  それ以上ある場合は「他にも軽微なスタイル指摘があるが省略する」と述べる。
- **同種の問題はまとめる。** 同じパターンの問題が 3 箇所以上あれば、
  代表例 1 つを詳述し「同様の問題が他に N 箇所」と書く。個別列挙しない。

---

## 入力の判定

レビュー対象の形式に応じて、チェックリストの適用範囲を調整する。

| 入力形式 | 重点チェック項目 | スキップしてよい項目 |
|---|---|---|
| スニペット・単一関数 | 正確性・エラーハンドリング・命名 | アーキテクチャ（10）・テスタビリティ（8） |
| ファイル全体 | 全チェックリストを適用 | なし |
| diff / PR | 変更行に焦点。周辺コードとの整合性も確認 | 変更に無関係なセクション |
| 設計・アーキテクチャ相談 | API設計（7）・アーキテクチャ（10） | 正確性のエッジケース（1）・リソース管理（6） |

- diff / PR の場合、既存コードの問題を発見したら指摘してよいが、
  「スコープ外の既存問題」と明示ラベルを付ける。
- 言語が判明したら `references/<lang>.md` が存在するか確認し、あれば参照する。

---

## 深刻度ラベル

レビュー全体で一貫して使用する。

| ラベル | 意味 |
|---|---|
| 🔴 **CRITICAL** | バグ・データ消失・セキュリティホール・データレース — マージ前に必ず修正 |
| 🟠 **MAJOR** | 重大な設計上の欠陥・パフォーマンスの崖・エラーハンドリング漏れ |
| 🟡 **MINOR** | 正確性のエッジケース・リソースリーク・混乱を招く命名 |
| 🔵 **NIT** | スタイル・慣用表現・軽微な可読性 — 簡単なら直す、そうでなければスキップ |
| 💡 **SUGGESTION** | 任意の改善提案 — 検討する価値はあるが、ブロッカーではない |

## レビューチェックリスト

各カテゴリを順番に確認する。明らかに該当しないカテゴリはスキップしてよいが、その際は明示する（例：「このスニペットに並行性の懸念はない」）。

### 1. 正確性

- ロジックは意図した動作と一致しているか？
- すべてのエラーパスが処理されているか？エラーが握り潰されていないか？
- オフバイワン・null デリファレンス・整数オーバーフロー？
- 事前条件・事後条件が守られているか？
- エッジケースのカバー：空入力・ゼロ・負数・最大値・並行アクセス？

### 2. エラーハンドリング

- すべてのエラー戻り値はチェックするか、明示的に破棄する（コメント必須）。
- エラーにはコンテキストを付与する（どの操作で何が失敗したか）。
- 同じエラーをログに記録 *かつ* 呼び出し元に返すことはしない — どちらか一方を選ぶ。
- エラーの種別は適切か（回復可能か、致命的か）？

### 3. 並行性とデータレース

- ロックなしで複数スレッド・ゴルーチンから共有ミュータブル状態にアクセスしていないか？
- スレッドセーフなデータ構造を使うべき場面で使っているか？
- 非同期処理のライフタイムは有界か？リークする可能性はないか？
- キャンセル・タイムアウトが適切に伝播されているか？

### 4. パフォーマンス

- ホットパスで不要なアロケーション・コピーが発生していないか？
- N+1 クエリパターンが発生していないか？
- キャッシュできるのに毎回計算・取得していないか？
- データ量に対してアルゴリズムの計算量は適切か？

### 5. セキュリティ

- SQL・コマンド・パスなど、ユーザー入力が直接組み込まれていないか？
- シークレット・トークンがログ・エラーメッセージ・URL に含まれていないか？
- 認証・認可チェックが存在し、正しく機能しているか？
- 入力バリデーション：長さ・文字セット・値域のチェックがあるか？
- 暗号化用途に非暗号論的乱数や弱いハッシュ関数を使っていないか？

### 6. リソース管理

- ファイル・DB 接続・ネットワーク接続が確実にクローズされているか？
- エラーパスでもリソースが解放されるか？
- ロック・セマフォはすべてのパスで解放されるか（早期リターン含む）？

### 7. API・インターフェース設計

- インターフェースは最小限の表面積か？不要なものを公開していないか？
- 関数シグネチャ：引数が多すぎないか？まとめられるか？
- 公開 API にはドキュメントが付いているか？
- 破壊的変更か、後方互換性のある変更か？
- 抽象化は適切なレベルか — 漏れすぎず、過剰設計でもないか？

### 8. テスタビリティとテスト（テストがスコープに含まれる場合）

- 外部依存（DB・ネットワーク）なしでテスト可能か（依存性が注入されているか）？
- 重要なパスとエラーパスのテストカバレッジは十分か？
- テストは実装の詳細ではなく振る舞いをテストしているか？
- テストに非決定的な要素（sleep・現在時刻・乱数）が含まれていないか？

### 9. 保守性と可読性

- 変数名・関数名が意図を伝えているか？
- マジックナンバーが名前付き定数に抽出されているか？
- 関数は概ね単一の責務に収まっているか？
- コメントは *何を* ではなく *なぜ* を説明しているか？
- `TODO`/`FIXME` は管理されており、放置されていないか？
- デッドコードが削除されているか？

### 10. アーキテクチャ・設計（大きなレビューの場合）

- この変更は既存のアーキテクチャに沿っているか？先に設計議論が必要なパターンを
  導入していないか？
- SRP：この関数・クラス・モジュールはひとつのことをやっているか？
- 結合度：このコンポーネントは他コンポーネントの内部を知りすぎていないか？
- ビジネスロジックがインフラ層（DB・HTTP ハンドラ）に漏れていないか？
- この変更は可逆か、それともロックインを生むか？

## 出力フォーマット

すべてのレビューを以下の構造で出力する。

```
## コードレビュー

### サマリー
2〜4 文：全体的な品質・最大の懸念・マージ可否の概要。
特筆すべき良い設計判断があれば、ここで 1〜2 文で触れる。独立セクションにはしない。

### 指摘事項

#### [ファイル名:行番号 または 関数名]

** [ID] 🔴 CRITICAL — [短いタイトル]**
[問題の内容・なぜ問題か・何が起きるか]

修正前：
[問題のあるコード]

修正後：
[修正後のコード]

[各セクション内で深刻度順に繰り返す]

### 判定
- [ ] 承認 — このままマージ可
- [ ] 軽微な修正後に承認 — NIT を対応後にマージ
- [x] 変更要求 — CRITICAL/MAJOR を解消してからマージ
- [ ] 設計議論が必要 — 根本的なアプローチを見直す
```

### 出力例

以下は Go コードに対するレビューの抜粋例。フォーマットと深刻度の使い分けの参考にすること。

```
## コードレビュー

### サマリー
HTTPハンドラ内でDBクエリ結果を返すシンプルな実装。エラーハンドリングに致命的な
欠落が 1 件あり、修正するまでマージ不可。全体の構造は明快で、ミドルウェア分離の
判断は適切。

### 指摘事項

#### ./path/to/file.go:42 — GetUser

**1 🔴 CRITICAL — rows.Err() 未チェック**
`rows.Next()` ループ終了後に `rows.Err()` を確認していない。
ネットワーク障害等でイテレーションが中断した場合、不完全なデータを
正常レスポンスとして返す。

修正前：
for rows.Next() {
    // scan...
}
return users, nil

修正後：
for rows.Next() {
    // scan...
}
if err := rows.Err(); err != nil {
    return nil, fmt.Errorf("iterating user rows: %w", err)
}
return users, nil

#### ./path/to/file.go:38 — GetUser

**2 🟡 MINOR — rows.Close() の defer 位置**
`rows.Close()` の defer が `err` チェックより前にある。
`db.Query` がエラーを返した場合、nil の rows に対して Close を呼ぶ。

修正後：
rows, err := db.QueryContext(ctx, query)
if err != nil {
    return nil, fmt.Errorf("querying users: %w", err)
}
defer rows.Close()

#### ./path/to/file.go:29

**3 🔵 NIT — マジックナンバー**
`if limit > 100` の 100 を名前付き定数に抽出する。

### 判定
- [ ] 承認
- [ ] 軽微な修正後に承認
- [x] 変更要求 — CRITICAL を解消してからマージ
- [ ] 設計議論が必要
```

---

## トーンのルール

- 直接的かつ具体的に。「42 行目で null デリファレンスが発生する」は良い。
  「null 系の問題があるかもしれない」は悪い。
- 埋め草フレーズを使わない：「全体的には良さそう」「いい感じ」「面白いアプローチ」。
- 明確なバグに対してぼかさない：「クラッシュする」であって「クラッシュするかもしれない」ではない。
- 意見には明確なラベルを付ける：「個人的には X を好むが、これでも問題ない」
  または「🔵 NIT — スタイルの好み」。
- 作者の時間を尊重する：関連する指摘はまとめ、1 つの問題を 5 つのコメントに
  分割しない。
